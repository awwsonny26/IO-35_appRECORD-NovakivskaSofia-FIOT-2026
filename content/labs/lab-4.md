**Тема:** Розширені можливості Node.js-додатків: логування, завантаження файлів, моніторинг продуктивності.

## Опис середовища розробки

Для виконання четвертої лабораторної роботи було використано Node.js, Express.js, MySQL, Sequelize ORM, а також пакети `morgan`, `winston`, `multer` і `pm2`. Базою для роботи став уже підготовлений серверний застосунок StudySpace, у якому раніше було реалізовано REST API, автентифікацію користувачів і централізовану серверну структуру на основі маршрутизаторів, контролерів та middleware.

У межах цієї роботи застосунок було розширено відразу в кількох напрямах. По-перше, додано HTTP-логування запитів та окреме логування подій і помилок у файли. По-друге, реалізовано завантаження одного або кількох файлів із серверною валідацією типу та розміру. По-третє, створено маршрут моніторингу стану процесу Node.js та окрему сторінку `/lab4-tools`, яка об'єднує статус сервера, форми завантаження і перегляд останніх логів у браузері. Додатково застосунок було перевірено при запуску через PM2.

---

## Основні можливості реалізованого застосунку

- логування всіх HTTP-запитів через `morgan`;
- файлове логування подій і помилок через `winston`;
- окремі файли `app.log` та `error.log` у каталозі `logs`;
- централізований запис помилок через `errorHandler`;
- вимірювання часу обробки кожного запиту через окремий middleware;
- маршрут `GET /api/status` для перегляду uptime, пам'яті, CPU та даних процесу;
- маршрут `GET /api/logs/recent` для перегляду останніх логів застосунку;
- завантаження одного файлу через `POST /api/uploads/single`;
- завантаження кількох файлів через `POST /api/uploads/multiple`;
- серверна валідація дозволених MIME-типів і обмеження розміру файлів;
- віддача завантажених файлів через статичний маршрут `/uploads`;
- окрема локальна сторінка `/lab4-tools` для демонстрації нових можливостей у браузері;
- підготовлені npm-скрипти для запуску застосунку через PM2.

## Хід виконання

### Підготовка проєкту та залежностей

На першому етапі до проєкту StudySpace було додано пакети `morgan`, `winston`, `multer` і `pm2`. Вони покривають логування HTTP-запитів, файлове логування подій, обробку файлів та керування процесом застосунку в режимі менеджера процесів.

```json
{
  "scripts": {
    "start": "node server.js",
    "dev": "node --watch server.js",
    "pm2:start": "pm2 start server.js --name studyspace",
    "pm2:logs": "pm2 logs studyspace"
  },
  "dependencies": {
    "morgan": "^1.10.1",
    "multer": "^2.1.1",
    "winston": "^3.19.0"
  },
  "devDependencies": {
    "pm2": "^7.0.1"
  }
}
```

Окрім цього, файл `.env.example` було доповнено змінними `LOG_LEVEL`, `MAX_UPLOAD_SIZE_BYTES` і `MAX_UPLOAD_FILES`, щоб параметри логування та завантаження файлів можна було конфігурувати окремо від коду.

### Реалізація файлового логування через Winston

Для професійнішої роботи з логами модуль `server/utils/logger.js` було перероблено на базі `winston`. У ньому створюється логер із JSON-форматом, часовими мітками та двома файловими transport-каналами: `app.log` для подій загального рівня і `error.log` для помилок.

```js
const logger = createLogger({
  level: process.env.LOG_LEVEL || 'info',
  format: format.combine(
    format.timestamp(),
    format.errors({ stack: true }),
    format.json()
  ),
  transports: [
    new transports.File({ filename: appLogFile }),
    new transports.File({ filename: errorLogFile, level: 'error' })
  ]
});
```

Додатково для dev-режиму було залишено виведення логів у консоль, а також підготовлено `stream.write()`, який використовується модулем `morgan`.

### Логування HTTP-запитів через Morgan

У файлі `server/app.js` до застосунку було підключено middleware `morgan('combined', { stream })`. Це дає змогу автоматично записувати всі HTTP-запити до того самого логера, який обслуговує файлові журнали.

```js
app.use(morgan('combined', { stream }));
app.use(performanceMonitoring);
```

Таким чином у застосунку поєднано два рівні логування: базове логування кожного HTTP-запиту та логування власних подій застосунку на кшталт health check або метрик продуктивності.

### Централізована обробка помилок і логування збоїв

Існуючий `errorHandler` було розширено так, щоб він коректно обробляв помилки `multer`, повертав JSON-відповідь клієнту та записував серверні збої через `logError()`.

```js
const statusCode = error instanceof multer.MulterError
  ? 400
  : error.statusCode || 500;

if (statusCode >= 500) {
  logError(error, {
    method: req.method,
    path: req.originalUrl,
    body: req.body
  });
}
```

Паралельно контролери категорій, курсів і raw SQL-демо було переведено на схему `asyncHandler + AppError`, щоб помилки передавалися в єдиний middleware-шар, а не оброблялися локально в кожному контролері.

### Вимірювання часу відповіді сервера

Для контролю продуктивності створено окремий middleware `performanceMonitoring`. Він вимірює час від початку обробки запиту до завершення відповіді і після цього формує інформаційний запис у лог.

```js
const performanceMonitoring = (req, res, next) => {
  const start = process.hrtime.bigint();

  res.on('finish', () => {
    const durationMs = Number(process.hrtime.bigint() - start) / 1e6;

    logInfo('Request performance metric recorded.', {
      type: 'performance',
      method: req.method,
      path: req.originalUrl,
      statusCode: res.statusCode,
      durationMs: Number(durationMs.toFixed(2))
    });
  });

  next();
};
```

Такий підхід дозволяє бачити не лише сам факт звернення до маршруту, а й реальний час його обробки, що важливо для аналізу продуктивності backend-застосунку.

### Реалізація завантаження одного та кількох файлів

Для роботи з файлами було створено модуль `server/middleware/upload.middleware.js`, у якому налаштовано `multer.diskStorage`, автоматичне створення каталогу `uploads`, обмеження розміру завантаження та перевірку MIME-типів.

```js
const upload = multer({
  storage,
  fileFilter,
  limits: {
    fileSize: maxUploadSize
  }
});
```

Сервер приймає лише файли форматів JPG, PNG і PDF. Для цього використано власну перевірку:

```js
const allowedMimeTypes = new Set([
  'image/jpeg',
  'image/png',
  'application/pdf'
]);
```

Після цього були створені два маршрути:

- `POST /api/uploads/single` - завантаження одного файлу;
- `POST /api/uploads/multiple` - завантаження кількох файлів в одному запиті.

Контролери повертають JSON із коротким повідомленням, метаданими файлу, його MIME-типом, розміром та збереженим шляхом у каталозі `/uploads`.

### Маршрут моніторингу стану сервера

Для спостереження за поточним станом процесу Node.js реалізовано маршрут `GET /api/status`. Він повертає JSON із основними технічними метриками: uptime, memoryUsage, cpuUsage, PID процесу, версією Node.js та платформою.

```js
res.json({
  status: 'ok',
  timestamp: new Date().toISOString(),
  uptimeSeconds: Number(process.uptime().toFixed(2)),
  memoryUsage: process.memoryUsage(),
  cpuUsage: process.cpuUsage(),
  process: {
    pid: process.pid,
    nodeVersion: process.version,
    platform: process.platform
  }
});
```

Цей маршрут є прямою практичною реалізацією завдання з моніторингу продуктивності та дає змогу швидко оцінити, як поводиться серверний процес у реальному часі.

### API для перегляду логів і браузерна панель моніторингу

Як додаткову частину лабораторної роботи було створено маршрут `GET /api/logs/recent`, який читає останні рядки з файлів `app.log` та `error.log` і повертає їх у JSON-форматі.

```js
const [appLogs, errorLogs] = await Promise.all([
  parseLogLines(appLogFile, limit),
  parseLogLines(errorLogFile, limit)
]);
```

На базі цього маршруту, а також `GET /api/status` і upload-endpoint'ів, було створено окрему локальну сторінку `GET /lab4-tools`. Вона містить:

- блок стану сервера;
- форму для завантаження одного файлу;
- форму для завантаження кількох файлів;
- блок перегляду останніх логів.

Така сторінка виконує роль простої панелі моніторингу та суттєво полегшує демонстрацію реалізованого функціоналу під час перевірки.

### Запуск застосунку через PM2

Для перевірки роботи серверного застосунку через process manager було використано `pm2`. Запуск виконувався локально з проєкту, після чого перевірявся статус процесу та виводилися його логи.

```bash
./node_modules/.bin/pm2 start server.js --name studyspace-lab4 --time
./node_modules/.bin/pm2 list
./node_modules/.bin/pm2 logs studyspace-lab4 --lines 20 --nostream
```

У результаті PM2 перевів застосунок у стан `online` та дозволив переглядати журнали запуску й логування без безпосереднього утримання процесу в активному терміналі. Це демонструє практичну користь PM2 як менеджера процесів для Node.js-додатків.
